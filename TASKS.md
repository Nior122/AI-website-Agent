### Open security limitations (accepted, documented, revisit before real customers)

- Reviewer identity is never *verifiable* in this system: `VERIFIED_IDENTITY_SOURCES` is empty by design, so no channel can currently produce `identity_verified: true` other than a local operator writing the approval file with `deployment.authorization.write_approval`. A real per-reviewer identity needs an authentication provider plus a `reviewers` schema change - both deferred until there is more than one human in the loop. Phase 49 widened *who may decide* without pretending to widen *how well we know them*: `/demo` in Telegram records a `PREVIEW_DEPLOYMENT` approval attributable to an allow-listed numeric user id, and the capability file it materializes still says `identity_verified: false`. A shared bearer token remains a client credential and is never accepted as a person's identity by any surface, including the send path, which records who asked (`send_actor`, `send_identity_source`) without treating that as authorization.
- One shared bearer token means no per-client rotation, no rate limiting, and no lockout; the API must stay on loopback or behind a private network, and `GET /healthz` is the only route that may be exposed publicly.
- The relational backend is exercised through the SQLite compatibility mode in this environment: no live PostgreSQL/Supabase instance, Vercel account, n8n server, or Render service was contacted, so provider-side authentication behaviour remains untested here.
- A sent email's fate past the provider is unknowable from this repository: `REPORTED_SENT` and `ACCEPTED_BY_PROVIDER` are the strongest available claims, and the second requires reading the id back through the read-only client. Bounce, complaint, spam-folder, and open tracking are not implemented because no provider here has been verified to expose them, and an inbox-owner signal would need its own adapter, contract, and consent story - not an inference from elapsed time, which this build refuses to record as a result.
- `data/tracking/state.json` is protected by test isolation (temporary copies, disposable state paths, and a byte-identity assertion in the Phase 40 end-to-end test) rather than by a store-level write guard.
- An inbound event's *sender identity* is not verifiable from here. The intake records what a provider says a business said, carrying the provider's event id and - when a secret is configured - a signature proving the bytes came from a holder of that key; neither proves the writer owns the lead it references. A caller who knows a `lead_id` and holds the token can therefore attach a fabricated message to that lead's history, which is why the route can assert nothing about approvals, deliveries, or outcomes, why every inbound response carries the human-review flag, and why the signature exists for anyone relaying events they do not control. A stronger guarantee needs provider-side verification of the sender against the recorded contact, which no code here performs.
