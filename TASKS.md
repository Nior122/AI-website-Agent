| Keep `preflight` free of sockets, provider calls, and DDL, and say so in `actions_not_performed` | The command has to be safe as the *first* step against a real workspace, including a production one; a readiness check that creates a job or reaches the provider cannot be trusted before the risky commands | 2026-10-15 |
| Report n8n starter placeholders instead of rewriting or refusing them | The repository copies are deliberately runnable demonstrations (its own tests run 01 and 02 unmodified), so the honest answer is "edit this in the n8n UI", visible before import - not a mutated export and not a broken test | 2026-10-15 |
| Rebuild the suite's workspace records from the verified review package in a temporary root | `data/tracking/state.json` is untracked by design, so reading it directly made a module pass or fail on whether another had run first; rebuilding in isolation removes the order dependence and the ability to write into the workspace under test without weakening an assertion | 2026-10-15 |
| Classify the publish ledger by what an entry reports, not by its position | A gate refusal and an operator resolution are bookkeeping; reading "the last line" let a refusal masquerade as the end of an in-flight publish and unblocked a blind republish. `latest_publish_attempt()` and the shared bookkeeping test keep uncertainty visible until the provider state is confirmed | 2026-10-15 |
| Require `--resolve-note` for `--resolve-uncertain-publish`, and record it before contacting the provider | An anonymous retry is unauditable, and a record written after the call is lost if the call is the thing that kills the process; the annotation stays `published: false` because a decision is not evidence about the provider | 2026-10-15 |
| Let the durable authorization pre-check honour the explicit resolve flag, and nothing else | Without it the only documented recovery path (CLI, worker) was unreachable because the advisory gate refused first; the publish boundary still re-verifies approval, validation, and the ledger, and a recorded resolution grants no standing permission | 2026-10-15 |
| Age `RUNNING` jobs from the newest recorded timestamp, and refuse to age one with no timestamp at all | Monitoring and recovery must use the same evidence or the two surfaces wait for each other forever; inventing an age for an undated claim would mark work recoverable on no evidence | 2026-10-15 |
| Keep the local n8n verifier loopback-only and turn its faults into node output | Every node header carries the API bearer token, so a non-loopback URL is a credential-exfiltration path rather than a runtime detail; and a workflow whose HTTP node raised a Python exception reports nothing to the operator, defeating the point of its failure branches | 2026-10-15 |
| Redact absolute paths from HTTP error answers only | Operators need repository-relative paths and preview URLs in CLI output to act, while a remote response must not map the host filesystem - so `redact_local_paths()` is applied at the HTTP boundary, not inside the store | 2026-10-15 |

### Open security limitations (accepted, documented, revisit before real customers)

- Reviewer identity is never *verifiable* in this system: `VERIFIED_IDENTITY_SOURCES` is empty by design, so no channel can currently produce `identity_verified: true` other than a local operator writing the approval file with `deployment.authorization.write_approval`. A real per-reviewer identity needs an authentication provider plus a `reviewers` schema change - both deferred until there is more than one human in the loop.
- One shared bearer token means no per-client rotation, no rate limiting, and no lockout; the API must stay on loopback or behind a private network, and `GET /healthz` is the only route that may be exposed publicly.
- The relational backend is exercised through the SQLite compatibility mode in this environment: no live PostgreSQL/Supabase instance, Vercel account, n8n server, or Render service was contacted, so provider-side authentication behaviour remains untested here.
- `data/tracking/state.json` is protected by test isolation (temporary copies, disposable state paths, and a byte-identity assertion in the Phase 40 end-to-end test) rather than by a store-level write guard.
